# 3D競馬ゲーム マルチプレイ版（フェーズ3.5：サーバー権威化＋デプロイ対応＋UI統一＋外部DB保存）

友達とリアルタイム対戦できる公開サーバー版。既存の1人用ゲーム（Museアーティファクト）とは別の、独立したNode.jsプロジェクトです。フェーズ1で対戦の土台（サーバー／ロビー／同期／ソロ）を構築し、フェーズ2で馬を簡易モデルから本物の彫刻3Dモデル（GLB）に差し替え、フェーズ3準備でゴール判定のサーバー権威化、公開デプロイ対応、クライアントUIの1人用版への統一を行い、フェーズ3.5でプレイヤーデータの保存を外部DB（PostgreSQL）対応にしました（方式3：無料のままデータを守る）。

## 馬モデル（フェーズ2）

- 採用モデル: **"Bay Horse" by vinish.dev**（https://vinish.dev/free-3d-models/horses）、**CC BY 4.0**（無料・商用可、ログイン不要で配布元からダウンロード）。GLB内の `asset.copyright` にも同クレジットが入っています。画面（ログイン画面・ホーム画面）にもクレジットを表示しています。
- 加工内容（CC BY 4.0の改変にあたるため明記）: アニメーションクリップを Idle / Gallop の2本に削減、メッシュを約50%に簡略化（103,646 → 52,285ポリゴン）、量子化して **4.59MB → 2.04MB** に軽量化。32関節のスキニングは維持。
- クライアントでは `SkeletonUtils.clone` で各馬を複製し、馬ごとに `AnimationMixer` で Idle（待機）／Gallop（レース）を再生。Gallopの再生速度は各馬の速度に連動。毛色は Coat マテリアルへのティント乗算で個体差を出しています（鹿毛・栗毛・青毛・芦毛など12パターン）。
- 自分の馬は一人称視点で首・たてがみ・耳が見え、他馬は全身が表示されます。
- Three.js 本体とアドオン（GLTFLoader / SkeletonUtils / BufferGeometryUtils）は `public/vendor/` に同梱し、CDNに依存しない構成にしました。
- GLBの読み込みに失敗した場合のみ、フェーズ1の簡易モデルにフォールバックします（コンソールに警告を出します）。
- 検証: ヘッドレスブラウザ（Chromium + SwiftShader）で実際にサーバー＋クライアントを起動し、ロビー画面とレース画面を撮影して目視確認済み（`screenshots/` フォルダ: phase2-home.png / phase2-lobby.png / phase2-race-early.png / phase2-race-mid.png）。レース序盤の画面では、一人称の自馬の首・耳と、前方の馬群（全身・毛色違い）が彫刻モデルで表示されることを確認しました。ソフトウェアレンダリング環境のため描画は重く、実機GPUでの操作感は未確認です。

## 起動方法

```bash
cd ~/workspace/keiba-multiplayer
npm install   # 初回のみ（ws / pg パッケージ）
npm start     # http://localhost:3000 で起動（PORT環境変数で変更可）
```

ブラウザで `http://localhost:3000` を開き、ニックネーム＋合言葉でログイン（初回は自動登録）。

プレイヤーデータの保存先は環境変数で切り替わります（詳細は後述「データ保存（外部DB）」）:
- `DATABASE_URL` を設定 → PostgreSQL（Supabase想定）に保存。再起動・再デプロイでも消えません。
- 未設定 → 従来どおり `data/players.json` にファイル保存（保存先は `DATA_DIR` で変更可）。

## 遊び方

- **ひとりで遊ぶ（ソロ）**: ホームで「ひとりで遊ぶ」→ 馬を選んで「レース開始」。部屋コード不要で、自分＋NPC17頭の18頭立てレース。そのまま1人用と同じ感覚で遊べます。
- **友達と対戦（マルチ）**: 「友達と対戦」→ ホストが「部屋を作る」と5文字の部屋コードが出るので友達に送る → 友達はコードを入れて参加 → 各自が馬を選んで全員「準備OK」でカウントダウン開始。最大8人、残りはNPCが補充して18頭立てになります。
- 操作: ペース4段階（おさえる／馬なり／攻め・小／攻め・大、キー1〜4）、左右移動（ボタン／←→キー）。スタミナが減ると失速します。

## 構成

```
keiba-multiplayer/
├─ server.js          # HTTP + WebSocket対戦サーバー
├─ store.js           # プレイヤーデータ保存アダプタ（PostgreSQL / ファイルの切替）
├─ public/
│  ├─ index.html      # ブラウザ用クライアント（Three.jsの一人称レース画面）
│  ├─ assets/
│  │  └─ bay-horse.glb  # 馬モデル（"Bay Horse" by vinish.dev, CC BY 4.0、軽量化済み 2.04MB）
│  └─ vendor/         # Three.js r160 本体＋アドオン（CDN非依存のため同梱）
├─ render.yaml        # Render デプロイ設定（無料枠前提）
├─ fly.toml           # Fly.io デプロイ設定（WebSocket対応・ボリューム永続化）
├─ data/
│  └─ players.json    # プレイヤーデータのファイル保存先（DATABASE_URL 未設定時のみ使用。保存先は環境変数 DATA_DIR で変更可）
├─ screenshots/       # 画面検証スクリーンショット（フェーズ2: phase2-*、フェーズ4: race-*）
└─ test/
   └─ test-flow.js    # 自動テスト（マルチ2人＋ソロ1人の全フロー）
```

### サーバー（server.js）
- 認証API `POST /api/auth`: ニックネーム＋合言葉で登録/ログイン。合言葉はscryptでハッシュ化して保存。所持金・解放馬・勝敗数などのプレイヤーデータは `store.js` のアダプタ経由で保存する（`DATABASE_URL` 設定時は PostgreSQL、未設定時は `data/players.json`）。
- WebSocketプロトコル: `hello`（トークン認証・再接続時は roomCode で元の部屋に復帰）/ `createRoom` / `joinRoom` / `soloStart` / `selectHorse` / `ready` / `pos`（位置送信）/ `backToLobby` / `leaveRoom`。配信: `room` / `countdown` / `raceStart` / `state`（全頭の位置、10Hz）/ `results`（サーバー確定の着順表）。
- NPC: サーバー側で1人用エンジン（keiba-engine.js）の走行シミュレーションを移植して計算（目標速度式・ペースAI・脚質3相・スタミナ・追走/前詰まりキャップ・進路判断・横移動の慣性まで1人用と同一数値）。旧モデル（baseSpeed＋脚質の2値係数、スタミナなし・即時加速）は「相手が速すぎて試合にならない」ため廃止した。
- ゴール判定（フェーズ3でサーバー権威化）: クライアントの距離申告は「前回受理からの経過時間 × 上限速度24m/s ＋ ジッター2.5m」の範囲でのみ受理し、超えた分は切り捨てて補正します（上限は1人用の実効最高速度＝持続約21.4m/s・ムチ過渡ピーク約23.8m/sに合わせて24に設定）。速度表示もサーバー算出値を使います。ゴール到達は、サーバーが検証した距離が2000mに達した時点でサーバー側が判定し、着順を確定します。クライアント申告のゴール通知という経路は存在しません（`pos` の検証が唯一の判定経路）。上限速度は環境変数 `KEIBA_MAX_SPEED` で変更可能（テスト時のみ緩和に使用）。
- レース終了条件: 全員ゴール、または最初のゴールから20秒で打ち切り。着順に応じて賞金・勝利数を保存データへ反映。

### クライアント（public/index.html）
- Three.js（`public/vendor/` に同梱）の一人称視点。自分の馬の首越しにコースと他馬を見るシーン（楕円オーバル2000m、ダート帯、他馬は補間で滑らかに移動）。
- 馬はGLBの彫刻モデル（上記「馬モデル（フェーズ2）」参照）をスキニングアニメーションで表示。モデル読み込み完了（最大6秒待ち）後に馬を配置します。
- ロビー画面（部屋コード表示・馬選択・準備OK・メンバー一覧）、結果画面（着順表・賞金）。

## データ保存（外部DB：Supabase + PostgreSQL）

Render無料枠には永続ディスクがないため、ファイル保存のままだと再デプロイ・再起動でプレイヤーデータ（所持金・解放馬・勝敗）が消えてしまいます。そこで保存先を外部DB（PostgreSQL）に切り替えられるようにしました（`store.js`）。`DATABASE_URL` を設定するだけで有効になり、**無料のままデータが消えなくなります**。

仕組み:
- テーブル `players`（`nickname` が主キー、`data` が JSONB）に、現行スキーマ（合言葉ハッシュ・ソルト・所持金・解放馬・勝敗数）を丸ごと格納します。テーブルはサーバー起動時に `CREATE TABLE IF NOT EXISTS` で自動作成されるため、事前のSQL実行は不要です。
- 起動時に全件をメモリへ読み込み、変更のたびにプレイヤー単位で upsert します（同一プレイヤーの書き込みは直列化）。終了時は書き込みキューをフラッシュしてから落とします。
- `DATABASE_URL` が不正・接続不可の場合は、データを守るためサーバーは起動を止めてエラーを出します（ログで気づけます）。

### (1) Supabase無料アカウントと接続文字列（DATABASE_URL）の取得

1. https://supabase.com で無料アカウントを作成する（GitHubアカウントでも登録可。課金なし）。
2. ダッシュボードで **New project** を押し、プロジェクト名とデータベースパスワードを決めて作成する（リージョンは東京 `Northeast Asia (Tokyo)` が近い）。作成完了まで数分かかる。
3. プロジェクト画面上部の **Connect** ボタンを押し、接続文字列（URI）をコピーする。サーバーからの接続には **Transaction pooler**（ポート6543）のURIが向いています。形式は次のようなものです:
   `postgres://postgres.<プロジェクトID>:[YOUR-PASSWORD]@aws-0-ap-northeast-1.pooler.supabase.com:6543/postgres`
   `[YOUR-PASSWORD]` の部分を、手順2で決めたデータベースパスワードに置き換える（パスワードに記号が含まれる場合はURLエンコードが必要）。
4. この文字列が `DATABASE_URL` です。**パスワードを含む秘密情報なので、GitHubリポジトリには絶対にコミットしないこと**（Render側の環境変数としてだけ設定します）。

### (2) Renderデプロイ時に DATABASE_URL を設定する

1. Renderダッシュボードで対象の Web Service を開き、左メニューの **Environment** を選ぶ。
2. **Add Environment Variable** で Key=`DATABASE_URL`、Value=手順(1)で取得した接続文字列 を追加して保存する。
3. 保存すると自動で再デプロイが始まる。再デプロイ後、サービスの **Logs** に `[store] 保存先: PostgreSQL (…pooler.supabase.com:6543/postgres)…` と出ていればDB保存が有効です。
   ※ `render.yaml` を使う Blueprint 作成時にも `DATABASE_URL` は入力欄として用意してあります（`sync: false` のため、値はダッシュボードで入力する方式です）。

### (3) これでどうなるか

- サーバーの実体（Render）は無料枠のままで、再デプロイ・再起動・スリープ復帰があっても、プレイヤーデータは Supabase 側に残り続けます。
- Supabase無料枠の範囲（DB容量など）は、友達数人規模の利用では十分な想定ですが、上限は Supabase の公式情報で確認してください。
- `DATABASE_URL` を外せば従来のファイル保存に戻ります（その場合の注意点は次の節のとおり）。

## デプロイ手順（Render、無料枠）

前提: このフォルダをGitHubリポジトリにpushしておくこと。設定ファイル `render.yaml` が同梱されています。

1. Render（https://render.com）にサインアップし、ダッシュボードで **New → Blueprint** を選ぶ。
2. 対象のGitHubリポジトリを接続すると、`render.yaml` を読み取って Web Service（freeプラン）が作成される。手動で Web Service を作る場合は Build Command=`npm install`、Start Command=`npm start`、Health Check Path=`/health` を設定する（サーバーは Render が渡す `PORT` 環境変数で待ち受けるため、ポート指定は不要）。
3. **プレイヤーデータを守るため、先述「データ保存（外部DB）」の手順で Supabase の接続文字列を取得し、環境変数 `DATABASE_URL` を設定する**（Blueprint作成時の入力欄、または作成後に Environment 画面から追加）。
4. デプロイが終わると `https://<サービス名>.onrender.com` のURLが発行される。そのURLを友達に送れば、ブラウザで開いて登録→対戦できる。
5. 動作確認: `https://<サービス名>.onrender.com/health` を開いて `{"ok":true,...}` が返ればサーバーは生きている。あわせて Render の Logs で `[store] 保存先: PostgreSQL (…)` と出ていることを確認する。
6. 更新方法: リポジトリにpushすれば自動で再デプロイされ、サイトが新しい版に切り替わる（レース中の切り替えは接続が切れることがあるため、レースの合間に）。`DATABASE_URL` を設定済みなら、再デプロイしてもプレイヤーデータは消えない。

無料枠の注意点（正直なところ）:
- **スリープ**: 無料枠のWeb Serviceは一定時間アクセスがないとスリープし、次のアクセスで起動に数十秒かかる。レース中のスリープはないが、友達を招待する前に一度開いて起こしておくとスムーズ。
- **データが消える問題（`DATABASE_URL` 未設定の場合のみ）**: 無料枠には永続ディスクが付かないため、ファイル保存（`data/players.json`、所持金・解放馬・勝敗）は再デプロイ/再起動で初期化される。対策は次の優先順:
  1. **（推奨・実施済み）外部DB（Supabase/PostgreSQL）に保存する**: `DATABASE_URL` を設定するだけ。無料のまま再デプロイ・再起動でもデータが残る。手順は前節「データ保存（外部DB）」。
  2. 有料プランでDiskを追加し、`render.yaml` 内のコメントアウト済み disk 設定を有効化して `DATA_DIR=/var/data` にする。
  3. Fly.ioにデプロイし、ボリューム（`fly volumes create keiba_data`）を `/data` にマウントする（`fly.toml` 設定済み。Fly.ioの無料相当枠の有無はデプロイ時点の公式情報で要確認）。

Fly.io向けには `fly.toml` を同梱済みです（WebSocket対応の http_service 設定、自動停止オフ、ボリュームマウント、環境変数 `PORT`/`DATA_DIR`）。手順は `fly launch` → `fly volumes create keiba_data --size 1 --region nrt` → `fly deploy` です。

## フェーズ18（2026-11-27）: 実速度の底上げ＋低fpsスロー化の解消＋速度のkm/h表示

実機フィードバック「60km/hも出ていない／進むのが遅い」「シンプルに走るのをもっと速く」「時速表記にしよう」への対応。調査で、体感の遅さには設計速度そのものより大きな実害要因が2つあることが判明した。

### 原因（実測）
1. **raceLoop の dt クランプによるスローモーション化（主因）**: クライアントは `dt = min(0.05, 実経過)` の単一ステップで、20fps未満では失われた時間ぶん自馬の進行が実時間から遅れた。実コード（stepPhysics抽出）での計測: 60〜20fpsでは完走116.4s（平均17.18m/s）だが、15fpsで155.2s（12.89m/s＝46km/h、0.75倍）、10fpsで232.8s（8.59m/s＝31km/h、0.5倍）。サーバー時刻で進むNPCとの差もこれが原因。1人用は `ceil(rawDt/0.05)` のサブステップで実時間に一致させており、マルチ版だけ移植漏れだった。
2. **速度表示が m/s の数値を無単位で表示**: HUDの「スピード」は `mySpeed.toFixed(1)`（例「17.0」）で、1人用の「61 km/h」形式と違っていた。速く走っていても数値上は遅く見える一因。
3. FOV（66+sf×7+追い2.5）・カメラ高さ2.52m・地面テクスチャ（蹄跡等は1タイル18m、1人用は7m相当でマルチ版のほうが粗い）・ラチ支柱間隔（約3.7m）は確認したが、今回は実速度と時間処理の修正を優先し、FOVは従来どおり1人用式のまま（sf の基準速度だけ倍率に連動）。

### 変更内容
- **時間処理（public/index.html `raceLoop`）**: 1人用方式に統一。実経過時間（上限1.2s）を最大0.05s刻みのサブステップ（最大24）に割り、物理・歩様位相・反則判定だけを複数回回す。描画・他馬補間・カメラ・位置送信（実時間約20Hz）はフレーム1回。スローモーション（ゴール前接戦0.68倍）は物理にのみ従来どおり適用。
- **実速度 ×1.2（`SPEED_MULT`、server.js / public/index.html で同値）**: 基準速度（NPCは名簿 base、プレイヤーは base/式）・速度キャップ（クライアント 24.0→28.8、サーバー検証 `MAX_SPEED` 24→28.8）・ゲート出遅れキャップ 4.2・好発ブースト 7.5・追走キャップの余量・横移動速度（プレイヤー/NPC/分離の押し出し）・ゴール後の減速（×倍率²で流し距離不変）を一律連動。**スタミナの毎秒消費にも ×1.2** を掛け、距離あたりの消費＝従来と同一に保った（速くなった分だけ温存が有利になる偏りを防止）。ペース熱（paceHeat）の基準速度 16.7 と幅 1.1 も ×1.2 し、ハイペース判定の効きを不変に保った。脚質補正・レーティング係数・馬場補正などの相対値はすべて不変。

## フェーズ19（2026-11-27）: 世界スケールの根本修正（コース周長とsim距離の不一致）＋歩様を1人用公式へ回帰

## フェーズ24: 一人称の「ぶっとい円柱」除去＋腕を左右に構える形へ

### 円柱の正体（実測で特定）
- 実機報告「画面中央にぶっとい円柱がある」の正体は、**騎手モデルの前傾した胴体（背中）そのもの**。フェーズ23は Head ボーンを scale 0.001 で潰すだけだったため、首から下（胴体上部）がカメラ直下に残り、画面下部中央を覆う大きな塊として見えていた（再現スクリーンショット `screenshots/phase24-id-baseline.png`。首だけ潰した比較でも塊は不変＝首が原因ではないことも実測で確認）。

### 方式の見直し: シェーダ discard → ジオメトリ分割（public/index.html）
- **第1案（シェーダ discard）は没**: スキニング関節インデックスをフラグメントシェーダへ渡し、腕チェーン以外の断片を discard する方式は胴体を消せたが、テクスチャ付きの肌マテリアルで discard 境界の微分が壊れ、腕が市松状のノイズまみれになった（閾値を変えても不変、土煙・影は無関係と切り分け済み）。シェーダ改変そのものを廃止した。
- **採用方式（ジオメトリ分割）**: `buildFpArmMeshes(vis)` が自騎手の初回一人称化時に、騎手の各スキンドメッシュから **前腕＋手チェーンが支配的な三角形だけ**を抜き出した複製メッシュを生成し、同じスケルトンに bind する（頂点属性は共有、増えるのはインデックスのみ。実測 2メッシュ・4,732三角形）。三角形の採用条件は「重心の腕影響 ≥0.5 かつ 全頂点の腕影響 ≥0.3」。
  - 上腕・肩は含めない: カメラ真下〜画面端で「引き伸ばされた黒い刃状」に化ける三角形の発生源だったため（腕メッシュ単独の表示切替で発生源を特定）。肘の切り口は画面下端の外に来る。
  - 全身メッシュ側は一人称の間だけ全マテリアルの `colorWrite=false / depthWrite=false` にして描かない（頭・首・胴体・脚・帽子まで完全に消える）。影はデプスマテリアル経由のため全身の影がそのまま残る。ボーンのスケール潰し（Head 0.001）も廃止した。
  - 三人称・観戦・リプレイでは腕メッシュ非表示＋全身の書き込み復帰で従来どおり。他人の騎手には一切触らない。

### 腕の構え: 首の左右に開き、手綱を握る手に
- `RIDER_FP_ARM` を変更: 上腕 z 差分 ±0.35→**±0.5**（両手を首の左右へ開く）、前腕 x −1.5→−1.45、手首に掌側への倒し（Hand x −0.45・z ∓0.2）を追加し、全指ボーンに屈曲差分 `FingerCurl: 0.8` を適用（`applyRiderArmDelta` を Hand・指ボーンまで拡張）。素のポーズの「開いた掌がカメラを向いて両手を突き出す」見え方から、「手の甲を上にして手綱を握る手」にした。手綱グリップは従来どおり手ボーン実位置へ毎フレーム追従。

## フェーズ25: 予測ガイド＋「今攻めろ！」合図／レース距離を本物仕様（1200/1600/2000/2400m）へ

### 予測ガイド（public/index.html）
- **`predictPaceRunout(pace)`**: 現在の状態から、そのペースを固定して走り切る簡易シミュレーション（dt=0.2s）を `stepPhysics` の target/drain 式そのままで回し、「スタミナが尽きる地点（ゴールまで残り m）」または「ゴールまで持つ（残スタミナ）」を返す。前詰まり・ムチ・ゲート出遅れは無視し、スリップ状態は現在値を固定する近似。

## フェーズ26: 「いつもゴール前で減速する」の原因特定と修正

ユーザー指摘「いつもゴール前で減速する。スタミナあるのに、なんで？」を受け、プレイヤー馬（`stepPhysics` を抽出して駆動）とNPC（サーバー `buildField`/`tickNpcs` を駆動）の速度トレースを残り500m〜ゴール後まで実測し、減速項を1つずつ数値化した。

### 原因1（主因・マルチ版だけの欠陥）: 接戦スローモーションがプレイヤーの時計だけを遅くしていた
- `raceLoop` は「ゴールまで70m以内かつライバルが4m以内にいる」と `timeScale = 0.68` を**プレイヤーの物理だけ**に掛けていた。NPCはサーバーの実時間で進むため、接戦のゴール前ほど自分だけ遅くなる。
- 実測: 最後の70mに要する実時間はスローモなし 3.53s → スローモあり **5.20s**。同速のライバルに対して実質約32m／約1.65秒の遅れになり、サーバーは申告位置で着順を判定するため演出でなく実害だった。18頭立てでは接戦条件をほぼ毎回満たすため「いつも」と感じられていた。
- 1人用では同一コードが**全馬に同じ時計**で掛かるため相対効果ゼロ（1人用が正）。マルチ版への移植時にプレイヤー単独の時計へ掛けてしまったのが移植ミス。
- 修正: スローモーションを撤去し `timeScale = 1` 固定（`frameTimeScale` は歩様コード用に常に1で残置）。

### 原因2: 逃げの仕掛け区間プロファイルに段差（両版共通・脚質固定）
- `STYLE_PROFILE`（クライアント）と `NPC_STYLE_PROFILE`（サーバー）の両方で、逃げだけ `kick: 0.986` が `mid: 1.004` より低く、残り330m（仕掛け開始）で目標速度が **−0.30 m/s（−1.84%）** 段落ちしていた。スタミナ・ペース無関係に発生。実測（逃げ・馬なり）: 目標 16.36→16.06（残り330m、スタミナ87.7時点）。
- 修正: 逃げの `kick` を自脚質の `mid` と同値 **1.004** に統一（他脚質のような末脚ブーストは付けない＝「逃げの末脚は平凡」という脚質個性は維持）。クライアント/サーバー両方を変更。

### 設計として残した減速（1人用と同一式・数値を明示）
- **疲労係数**: スタミナ35未満で `0.80 + 0.20×(s/35)`。攻め大を残り430mから続けた場合、先行でゴール時 −5.9%（スタミナ23.6、係数0.935）、差しで −9.6%（スタミナ17.3、係数0.899）。スタミナ切れによる失速として従来どおり維持。
- **paceHeat の仕掛け補正**: paceHeat > 0.25 のとき逃げ/先行 ×0.994（最大 −0.6%）。レース形状の仕掛けとして維持。
- **最終コーナー係数**: コース形状上、最後のコーナーは全距離で残り約345m区間。速度値ではなく進む距離への係数で、外（lat −8）×0.932／内（lat +8）×1.078。完走タイム実測 129.25s（外）/ 126.00s（中央）/ 122.85s（内）。
- **前詰まりキャップ**: 前の馬の3.6m以内では目標がその馬の ×0.995（内では ×0.962）に制限。交通事情として維持。
- ゴール後の減速は両版とも `dist >= raceDist` でのみ開始しており、ゴール前への漏れは無いことを確認した。
